# ADR 0002: Server-Sent Events for the race stream

- **Status:** Accepted
- **Date:** 2026-10-19
- **Deciders:** POLARIS team

## Context

The Agent Race is the demo. The user submits one request and watches two lanes run: the
baseline that ships all 240 tool schemas to Bedrock, and Polaris that ships one to six. The
interesting part is not the final numbers, it is that the Polaris decision arrives **first**,
and then the baseline keeps counting while Polaris is already answering.

That requires a live feed, not a request/response pair. WebSockets would work, but the stream
is one-directional: the client only ever receives.

## Decision

Use **Server-Sent Events** over `GET /api/race/:id/stream`.

Seven event types make up the contract: `decision`, `shortlist`, `lane_start`, `lane_tokens`,
`lane_done`, `final`, `error`. Each event is a JSON object carrying `runId`, a monotonic `seq`
and an ISO `ts`.

The event schema lives in `packages/contracts` and is shared by the server, the web app and
the recorded flights. A recorded flight is a JSON array of exactly these objects, so one
reducer serves both the live stream and the replay.

## Consequences

- SSE is plain HTTP. It passes through Caddy, it needs no extra library on either side, and
  it reconnects on its own in most browsers.
- **The proxy must not buffer the stream.** The Caddyfile disables buffering on the stream
  route. A buffering proxy turns the whole demo into a single dump at the end.
- The browser connects to the EC2 hostname directly for the stream, not through the Vercel
  proxy, because a serverless function would buffer and then time out.
- SSE is one-directional. If a future feature needs the client to steer the race, that is a
  reason to revisit this decision, not a reason to plan for it now.
- `seq` makes the reducer robust against out-of-order delivery and lets a replay be resumed
  from a known point.
